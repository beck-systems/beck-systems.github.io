/sf-ticket (opens in a new tab)

A gated, multi-agent Salesforce delivery loop on Claude Code, run with one command.

  1. 01 Read-only · gate

    Intake Ticket, Slack thread, or pasted text. The operator confirms the lane.

  2. 02 Read-only

    Investigate Org state and repo history. The hook blocks writes.

  3. 03 Read-only

    Verify Every claim graded confirmed, plausible, or refuted.

  4. 04 Human gate

    Spec A person approves. The spec is locked by hash.

  5. 05 Sandbox

    Build The only stage that changes metadata, in a sandbox and its own worktree.

  6. 06 Checks

    QA Derived from the spec, before anything is promoted.

  7. 07 Human gate

    Promote Gearset. A person says go before it moves forward.

  8. 08 Human gate

    Close-out Jira, Confluence, and Slack.
  • Read-only, hook-enforced
  • Metadata changes in the sandbox only
  • A person approves

/sf-ticket takes a Salesforce request — a ticket, a Slack thread, or pasted text — and runs it through the same loop every time. Six specialized agents do the work. Hooks written in Python, not prompt instructions, decide what each agent is allowed to touch, and a human approves every outward or irreversible step.

The design pulls find apart from fix. Four agents are read-only, enforced by a hook. Only the builder changes metadata, and only in a build sandbox and its own git worktree. The approved spec is hashed; if the spec changes after approval, the builder's hook refuses to deploy. A verifier re-runs the queries itself and grades every claim confirmed, plausible, or refuted before any spec is written. Company-specific paths and org aliases live in two config files, so the workflow can move between orgs unchanged.

Lanes — support, explain, change, bug, and GTM — decide which stages run. The GTM lane does not build.

v1 has been used on real support, change, and bug tickets. Not built yet: unattended intake, builds for the GTM lane, and a dashboard of case-file frontmatter.

Salesforce Field Audit (opens in a new tab)

A Claude Code skill that shows which custom fields are actually used — and which are safe to deprecate.

It audits field usage on any Salesforce object: which custom fields are populated, how that has changed in the last twelve months, and which ones look abandoned. I built it after a run on a production Account object with roughly 300 custom fields accumulated over a decade of integrations, where 38% were dead, near-dead, or quietly abandoned, most of them left behind by a handful of decommissioned managed packages.

The live-query work — schema introspection, batched SOQL, recovering fields that cannot be aggregated, deciding what "inactive" means on an unfamiliar object — is driven by the model. Thresholds, package-namespace grouping, and report rendering are ordinary Python, so the rules do not drift from run to run. Parallel subagents fan out the expensive queries, which is why a ~300-field audit finishes in minutes. Output is a Markdown findings report plus a self-contained, searchable HTML field ledger.

Account Territory Management (opens in a new tab)

Configurable Salesforce territory assignment, with a Lightning admin UI and a full audit log — no deploy required to change a rule.

When an Account is inserted or updated, the engine evaluates active geographic territory rules in priority order — business line plus country and state, with blank fields as wildcards — and assigns an owner. Accounts that match no rule fall through to a per-business-line round-robin pool. Every attempt is written to an immutable assignment log. Admins manage rules, rotations, and manual overrides from a Lightning Web Component, and a custom permission lets integration users bypass the trigger.

The assignment service is bulk-safe: one SOQL and DML pass, no per-record queries. Test classes cover the controller, service, and end-to-end trigger path. It is a shipped Salesforce DX project.

GTM Intelligence Agent (opens in a new tab)

A Claude API CLI that researches a company and a role, then writes a structured briefing and outreach opener.

  1. 01 Company. Web search.
  2. 02 Role. Fetches a posting URL when it can.
  3. 03 Synthesis. No search. Snapshot, fit signals, talking points, and a draft opener.

A small, complete tool built directly on the Anthropic API — no agent framework and no low-code builder. The point is the architecture: deciding the workflow shape and what data moves between calls, instead of one freeform prompt.

I built it in five documented days, from a basic API call through tool use, chaining, a real CLI, and page fetch for job URLs. Login-walled postings fall back to search and come back thinner.

Approach

A personal method for spec-driven development on Salesforce. It is not a published program.

The spec is the deliverable. The org is the truth. Agents draft; humans approve; nothing reaches production without a person pressing the button.

Unlike repo-based spec-driven development, the live Salesforce org — not git — is the source of truth. That calls for three artifacts most software work skips.

  1. Org baseline

    As-is automation and the order of operations.

  2. Impact analysis

    Salesforce has no compiler for this. The analysis is what shows what a change will touch.

  3. Deployment and rollback

    Deploys are neither atomic nor reversible, so the plan belongs in the spec.

Separately, I use Tailscale as the network backbone of a personal local AI setup, SSHing into my home computer and running agentic development sessions in Termius.
